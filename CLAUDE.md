# EDGEmobile: notes for Claude sessions

EDGEmobile is a phone operating system for Cyberpunk 2077, built as REDnode apps (this repo has two packages: `edgemobile`, the server, the OS and the window for connecting a phone, and `edgephone`, the phone in the game, which gets its screen through EDGEmobile's service): one phone shown in the game (REDnode's overlay and HUD) and on the player's real phone (a web app reached through a Cloudflare quick tunnel, paired by QR code and a pairing code, installable as a PWA). Read [docs/design.md](docs/design.md) first. It depends on [REDnode](https://github.com/Edgemodders/REDnode), checked out beside this repo at `../REDnode`; read that repo's CLAUDE.md for the runtime, the tests and the conventions.

## Conventions

The same as REDnode's:

- **Commits:** straight to `main` and push, in small logical commits, after agreeing the plan in chat.
- **Git identity:** set per repo to `CyberbuildsAI` with the GitHub no-reply email. Never change the global identity.
- **Writing style:** plain, short sentences, tables for comparisons. Mark anything unverified as unverified.
- **Never commit game files** or data extracted from them, Cloudflare's `cloudflared` program, or a player's paired phones.
- **Security:** a paired phone may use only what EDGEmobile and its mobile apps offer, never REDnode's `api`, its MCP server or files. The server listens on `127.0.0.1` only. Any change to pairing or the tunnel gets the rules in docs/design.md, "Pairing and security", checked again. A phone gets in only with both the QR link's one-time key and the approval of someone at the PC (the user's rule, 2026-10-29). Once paired, it comes back by signing the PC's challenge with its key, with no key and no Allow (the M2 plan, agreed 2026-10-29).
- **Wording about the tunnel (the user's rule, 2026-10-29):** never "exposes" or "open to the internet". Say "a private web address" or "reachable from your phone", and always say in the same place how others are kept out (the two conditions), so it does not read as reckless.
- **Changelog:** `docs/changelog.md`, the Edgemodders convention (a line under **Unreleased** with each change a player would notice).
- **README at each release (the owner's rule, 2026-11-03; the same in every Edgemodders repo):** before each release run, update README.md's status line so it names the version (`**Status: <version> released on <date>** ...`) and draw the status badge again (the `status` entry in `tools/brand/badges.py`, then `python -I tools/brand/badges.py docs/assets/brand/badges`; the README's `<img alt>` too). `tools/release/readme-check.mjs` is REDnode's file, copied as it is (change it in REDnode, then copy it again). When the first release workflow is written, it runs `node tools/release/readme-check.mjs --version <v>` before building, on release runs only, as REDnode's release.yml does (step "The README says this release"), so a README that does not name the version stops the release. Between releases, keep the status line and the badge current with the phase.
- **EDGEweb's pages at each release (the owner's rule, 2026-11-21, EDGEmobile #2; the same in every Edgemodders repo):** right after each release with a version number (EDGEmobile's or Chooms!'s), in the same piece of work, this session brings EDGEweb's pages about that tool up to the version; EDGEweb's session does not wait to notice. In the sibling checkout `../EDGEweb`: the tool's wiki section `docs/wiki/<tool>/`, its rows on the shared wiki pages (`wiki/library.md`, `wiki/glossary.md`, `wiki/first-hour.md`, `wiki/faq.md`), its card on `docs/index.html` and its section on `docs/platform.html`. Until it has a wiki section, the pages that mention it (`grep -rlin -e edgemobile -e chooms docs`; on 2026-11-21 only the dashboard did). What changed is the release's section of `docs/changelog.md` or `docs/chooms/changelog.md`. Set each changed page's `reviewed` date, follow EDGEweb's `CLAUDE.md` (Wiki) for front matter, terms and screenshots, then commit and push to EDGEweb's `main` as `CyberbuildsAI`, as with the dashboard. It follows releases, never `main`: pages describe what players can install. One exception, the user's choice of 2026-11-22: the launch's pages are written before it (docs/design.md, "Docs plan"), each with EDGEdir's line "**EDGEmobile is not released yet.** This page describes what is built on its `main`...", which the release's wiki step takes off. The release steps, with this one as step 5, are in docs/design.md, "Release steps". A Claude session writes it, so it is a session step, not a step in `release.yml`.
- **For the next release's wiki** (what a player or modder would notice, unreleased, with the pages it touches; emptied by the release's wiki step): until the launch, everything (the sections are new; docs/design.md, "Docs plan"). After the launch, add a line here with each change.
- **REDnode needs:** what EDGEmobile needs from REDnode goes to REDnode as a `request` issue, with the shape that would work (docs/design.md, "What it may ask of REDnode").

## Dashboard (EDGEweb)

The platform dashboard at https://edgemodders.ai/dashboard.html draws one file in the EDGEweb repo, `docs/assets/dashboard/status.js` (plain JSON after the equals sign, one object per tool under `tools`). The owner and a managing session read it to see every tool's state, so EDGEmobile's entry is kept current by the session that works on EDGEmobile.

- **When:** in the same piece of work as any change to EDGEmobile's status: a phase built or done, a hand test added, run, passed or failed, a release, something EDGEmobile starts or stops waiting on, something only the owner can do.
- **How:** in the sibling checkout `../EDGEweb`, `git pull`, edit only EDGEmobile's object, set its `checkedBy` to this session and the date, bump the `?v=` on the `status.js` script tag in `docs/dashboard.html`, commit and push to `main` (as `CyberbuildsAI`). Leave `issues`, `lastTag`, `lastTagDate`, `lastCommit` and `commitsSinceTag` alone: EDGEweb's `tools/dashboard/refresh.py` writes those.
- **Words:** phases are `done`, `built, tests pending`, `in progress` or `planned`; tests are `passed`, `not run`, `partly run` or `failed`. The fields are described in EDGEweb's `CLAUDE.md`, under Dashboard.
- **Honest:** never mark a test passed or a phase done that this repo's own docs do not. A test with a step still to run is `partly run`.
